# 导出 PDF

「另存为 → PDF」打开的是一个**自己的导出界面**：左边设置、右边一叠分好页的 A4 纸，
底部一条状态栏写着共几页。两条出口：

| 按钮 | 走什么 | 什么时候用 |
|---|---|---|
| **保存为 PDF** | 后端的 `print_pdf` → WebView2 的 `PrintToPdf` | 默认。**不弹任何打印对话框**，选个路径就出文件 |
| **用系统打印机…** | `window.print()` | 要打真纸、要选别的打印机、要 N-up 时 |

## 为什么不用 `window.print()`

那条路必然弹系统打印对话框：用户得自己挑「Microsoft Print to PDF」、再去「更多设置」里
取消页眉页脚 —— 每一步都可能把结果弄成另一副样子，而代码里既看不到也管不了。

`ICoreWebView2_7::PrintToPdf` 直接写文件，页眉页脚 / 缩放 / 纸张 / 边距 / 方向 / 背景色
都在 `ICoreWebView2PrintSettings` 上（`src-tauri/src/pdf.rs`）。参数**逐项 clamp** 再交给
COM，等完成回调（60 秒超时）才报成功 —— 不然用户会拿到半截文件。

> ⚠️ 命令必须声明 `async`：`with_webview` 的闭包在主线程上跑，同步命令也在主线程上等，
> 那就是自己把自己锁死。另外 `windows` 这个 crate 是**必须**的直接依赖 —— `webview2-com`
> 的完成回调宏展开成 `::windows::core::Result`，那个路径得在我们自己的 crate 里解析得到。

## 分页是自己算的（`paginate.ts`）

预览里的一叠纸**不是**「一条长卷 + 几条虚线」，而是真的把内容摆进一张张固定大小的纸里。
这么做的原因：虚线是**估的** —— 真正的分页在打印那一刻才由排版引擎决定。

自己算之后：**预览就是产出**。打印时一张纸一个盒子 + `break-after: page`，PDF 的每一页
与预览的每一页逐页对应。

量法是**不看 margin 的**：把块 append 进当前页，然后看 `scrollHeight > clientHeight`。
行高、外边距折叠、图片高度全交给排版引擎，我们只读结果。切块：

- **表格按行切** —— 表头每页重画一遍，不然第二页开始的数字没有列名；
- 其它块**按行二分切**（`Range.extractContents()` 负责重建祖先链，手工搬节点最容易写出
  「标签对不上」）；
- 切不动的（一张特别高的图）**让那页长高**，绝不裁内容 —— 界面上会提示「有内容超出一页」。

### 六个踩过的坑

1. **打印时纸必须缩回「内容盒」**。第一版纸上带着页边距的内边距，一个 210×297 的盒子往
   170×261 的可打印区里塞 —— 实测 **5 张纸印成了 12 页**。
2. **量完还得再量一遍**。第一次排版时字体可能还没换好，用替身字体量的行高是错的 ——
   同一份内容字体就位前后差了**整整一页**（5 → 6）。`PrintView.settled` 就是那第二次排版，
   面板拿它刷新页数，写文件之前也必须 `await` 它。
3. **`box-sizing`**：`width: 210mm` + 左右各 20mm 内边距，在默认的 `content-box` 下就是
   250mm 宽的「纸」，比 A4 还宽。应用里 Tailwind 的 preflight 恰好兜住了，但代码里写死。
4. **表格几乎不会直接是顶层块**：预览把它包在 `my-3 relative group` > `overflow-x-auto`
   里。只认顶层 `tagName === "table"` 的话，一张大表格会被当成「切不动的 div」，按文本行
   硬切 —— **表现是表格在页底被生生截断**。所以往下找那张表（有且只有一张、且占了块高度
   一大半才算），切完把包装链照原样套回续页那一半。
5. **放不下就就地切**，别整块挪到下一页 —— 否则标题后面接一张大表格时，第一页只剩标题
   加一大片空白。
6. **`@page` 只写边距，不写 `size`**：纸张与方向已经在打印设置里给了，两处都写就是互相
   打架，而 CSS 那一条还不一定生效（Chromium 要 `preferCSSPageSize` 才认）。

## 配色三档

用户定的语义，**三条都是「尽量少动」**：

| 档 | 该做的 | 不该动的 |
|---|---|---|
| **原样**（默认） | 屏幕上什么样就印什么样 —— **包括底色**（`--color-cloud`，也就是你自己在 `src/styles/custom.css` 里改过的那一层） | 什么都不动 |
| **白底** | 只把**背景**换成白（纸 + 表格行 / 代码块那层底纹） | 字体、字号、行距、文字颜色 |
| **黑白** | 只把**颜色**去掉，**明度一个都不动** | 明暗关系（浅灰还是浅灰，深红变成同亮度的深灰） |

⚠️ 「白底」**不是**「换成浅色主题」：早期版本顺手把整套浅色板钉上去（含
`font-family: serif` / 字号 / 行距 / 逐个标签的 `color: … !important`），结果换个底色连标题的
字体和正文的颜色都跟着变 —— 用户报过这个。现在只重声明 `--color-cloud` /
`--color-paper` / `--color-paper-warm` / `--color-paper-deep` 四个**背景**变量。

⚠️ 代价：**深色主题下选「白底」会是白纸浅字**（文字颜色归 `--color-ink*`，那一档不碰它）。
这是「只改背景」的必然结果 —— 深色主题下想打浅色纸，用「原样」再自己调主题。

### 黑白：为什么是 JS 不是 CSS

两条看着最省事的路都试过，都不行：

- ❗❗**`filter: grayscale(1)`** —— 语义最直白（它本来就是按亮度加权的），但 Chromium 会把
  整棵子树**先栅格化成一张图**再印。实测：8 页纯文字的文档 **49KB → 1.07MB**（22 倍），
  真实长笔记那份是 31KB → 11.8MB。那正是「导出来怎么变成图片了、还选不中字」的来源。
- ❗❗**`mix-blend-mode: color` 盖一层中性灰** —— 在屏幕上语义是对的（取浮层的色相饱和度、
  取底下的明度），但**打印路径直接忽略混合模式**：实测印出来整张纸就是 `#808080`，
  也就是浮层自己的颜色，一点没混。

所以现在是**渲染时把每个元素的计算颜色就地换成同明度的灰**（`printView.ts` 的
`grayOutTree`，只在黑白档跑）：读 `color` / `background-color` / 四条 `border-*-color`，
**先读完再写**（边读边写会每步触发一次样式重算）。文件大小回到 50KB 那一档，字还是字。

> ❗❗**换算交给浏览器，别自己解析颜色。** 第一版是按 Rec.709 加权
>（`0.2126R + 0.7152G + 0.0722B`）自己算的，只认 `rgb()`/`rgba()`，于是**漏了一整类颜色**：
> Tailwind 4 的 `/透明度` 修饰符全都编译成 `color-mix(in oklab, …)`，而计算样式给出的是
> **`oklab(0.628 0.225 0.126 / 0.7)`** —— 连形状都不是 `rgb(...)`。用户截图里那行粉字、
> 那个 `.csv` 小标签就是这么留在「黑白」档里的。
>
> 现在用 **CSS 相对颜色语法**：`oklch(from <原色> l 0 h)` —— 取原色的感知明度 `l`、
> 彩度压成 0。一行通吃 rgb / hsl / oklab / `color(display-p3 …)`，alpha 也自动保留。
> 而且 `oklch` 的 `l` 是**感知明度**，比在线性空间加权更贴「看起来一样亮」：纯红在 OKLCH
> 里 L ≈ 0.63，换成中灰 `rgb(136,136,136)`；按 Rec.709 算会得到 `rgb(54,54,54)` 那种发黑的
> 红，明显偏暗。
>
> 兜底也是安全的：万一浏览器不认这条语法，`color` 声明整条失效，那个元素保持原色 ——
> 不会变成黑块。

验法同上（读像素），另外加一条**更狠的判据**：整页扫一遍，**`R≠G` 或 `G≠B` 的像素占比
必须是 0.00%**。实测 8 页文档：`rgb(136,136,136)` 占 59.1%，非灰像素 **0.00%**。

### 纸的颜色：跟着 `--color-paper`，不是在 CSS 里写死白

「原样」档的纸色就是 `var(--color-paper)`。主题、或者 `src/styles/custom.css` 改过它的时候，
屏幕上是一张调过的纸 —— 导出必须印成同一个颜色。

> ❗**这里踩过一次**：打印那几条规则原来都带着 `background: #ffffff !important`（`html` /
> `body` / 纸各一条），于是「原样」档**永远印成纯白** —— 屏幕上是他调过的纸色、导出的 PDF
> 却对不上。用户报的就是这个。浅色 / 黑白两档**不需要**写死白色：`PAPER_CSS` 已经把
> `--color-paper` 钉成 `#ffffff` 了。现在 `.floral-sheet` 那条干脆不写 `background`，
> 让它用 `SCREEN_CSS` 里那句 `var(--color-paper)`。

验证方式（不启应用）：把 `printView.ts` 用 esbuild 打个包，写个小页面**调用真的
`mountPrintView`**，再用 Edge 的打印管线出 PDF，最后**用 pdf.js 画出来读像素**：

```bash
npx esbuild src/features/pdfExport/printView.ts --bundle --format=esm --outfile=printview.mjs
# 页面里把 --color-paper 设成刺眼的红，然后：
msedge --headless=new --disable-gpu --virtual-time-budget=6000 \
       --no-pdf-header-footer --print-to-pdf=out.pdf "http://127.0.0.1:8099/printbg.html?mode=as-is"
```

实测结果：`as-is` 印出来正中是 `rgb(255,0,0)`（用户的纸色），`light` / `mono` 是
`rgb(255,255,255)`。读像素比看截图靠谱 —— 截图会「陈」，颜色更是看不准。

> ❗**`@page` 留出来的那圈页边上不了色**（别再试了）：`html` / `body` 的背景压根铺不进去，
> 换成固定定位、`inset: -100mm` 的伪元素也只盖住一小块 —— Chromium 的 `@page` margin box
> 不在 CSS 的绘制范围里。所以那圈一直是白的，**纸本身**的颜色才是要紧的。
> （真要四周都满色，只能把边距设成 0，让纸铺满整页。）

## 零碎但要紧的

- **图片要先摘掉 `loading="lazy"`**：屏幕外的图在打印那一刻根本没开始加载，PDF 里是空白。
- **面板与那张纸都不许盖住标题栏**：主窗口 `decorations: false`，顶上那条 `h-11` 就是
  **拖窗口的手柄**，盖住它用户的第一反应是「窗口拖不动了」。
- **设置记在 `localStorage`**（`floral.pdfExport.settings`），逐项校验后回填 —— 某个字段
  坏了不该让整份设置回落到默认。
- **Ctrl + 滚轮**缩放预览（40%–200%）。只影响眼睛，不影响产出。
- **Ctrl+滚轮要用原生监听 + `{ passive: false }`**：React 的 `onWheel` 挂在被动监听上，
  里面 `preventDefault()` 无效 —— 结果是预览缩了、整个 WebView 的页面缩放也跟着变了。
- **不要 `window.print()`** 之外再去动 WebView2 的 ScaleFactor：缩放是用 CSS `zoom` 加在
  版心上做的，这样分页是按缩放后的版心算的，预览与产出用同一套换算。

## 还没做

- **每张纸打印的页数（N-up）**：WebView2 的打印设置里没有这一项，只有系统打印对话框有。
- 页眉页脚在**预览**里是近似画出来的：真打出来那两行由 WebView2 画在可打印区外面，
  字体与位置不完全一样（页码是它按当前页/总页数画的，文案改不了）。
- 目录、页码起始值、双面打印。
