# 导出 PDF

「另存为 → PDF」打开的是**左边设置、右边预览**的面板：纸张、边距、缩放、页眉页脚、
标题、配色在左，右边是排好版的一页页纸。

## 右边的预览是什么

**不是我们画的近似图**，而是后端刚用 `PrintToPdf` 排出来的那份 **PDF**：

1. 面板把「标题 + 正文」摆成一份**不分页**文档（`mountPrintDocument`）；
2. 调 `print_pdf_preview` —— 与「保存为 PDF」**同一套参数**、同一套排版，只是写到临时文件、
   把字节直接还回来（Tauri 的 `ipc::Response`，前端拿到 `ArrayBuffer`）；
3. 前端用 **pdf.js**（`pdfjs-dist`）把字节画成 canvas。

所以**预览就是产出**：页数、断点、表格在哪里切，全由浏览器的排版引擎决定。
换设置时会重新生成一版（防抖 400ms），旧的那版留在屏幕上，不闪白。

> ⚠️ 同一时刻**只能有一份打印文档**挂在页面上 —— `PrintToPdf` 印的是整个 webview，
> 而打印 CSS 只留下 `.floral-print-root` 那一层，两份同时在就会被印进同一份 PDF。
> 所以预览、保存、打印全部排进同一个队列（`PdfExportPanel` 的 `runExclusive`）。
>
> 那份文档在屏幕上是**扔到视口外**的（`left: -100000px`）：它只给打印引擎看，
> 打印时 `@media print` 会把 `position` 改回 `static`、宽度改回 `auto`。

### 预览怎么看

- **Ctrl + 滚轮**缩放（40%–300%），以**指针所在处**为锚点：先把指针在内容坐标里的位置记下来，
  缩放后用同一个比例把那一处挪回指针底下。
- **空格 + 左键拖动**平移（两个方向）。
- 放大后横向、纵向都能滚。`zoom` 加在滚动容器**里面**那一层 —— 加在容器自己身上，
  容器会被放大而 `scrollWidth` 不跟着涨，右边那半截就永远滚不到（旧预览踩过这个坑）。
- 缩放先用 CSS `zoom` 立即生效；停手 300ms 后再按新的缩放**重画一遍 canvas**
  （最多 2 倍分辨率，再高只吃内存）。重画只改 canvas 的像素尺寸、不改 CSS 尺寸，版面不跳。
- 所有绘制排成**一条队**：`page.render()` 不能在同一个 canvas 上并发，而「换一份 PDF 后
  逐页画」和「缩放停手后重画」随时会撞上。
- **缩小时保持居中**：不能用 `margin-inline: auto` —— `zoom` 会把外边距也按比例缩掉，
  自动算出来的那点留白再被缩小，纸就贴到左边去了。现在是按**缩放后的实际宽度**反算左边距
  （`frameWidth * (1 / zoom - 1) / 2`）。实测 56.4% 时左右各留 136px；放大时边距归零、
  右半边可以滚。
- 右下角显示缩放百分比，点一下复位。

## 为什么不再自己分页

早先做过一整套：把内容真的摆进一张张固定大小的纸里，自己算断点、自己切表格和长段落。
它「预览即产出」，但有一个绕不过去的短板 —— **遇到整块切不动的东西就只能整块挪页**。
用户的笔记里到处是「一条列表项里塞着几张图」，这种块比一页还高，切不开，于是本页留下
大半空白、下一页才开始；浏览器按行盒排，能贴得紧得多。

试过几轮（按行二分切、按子块切、递归进列表项……），仍然对不齐。用户定调：
**既然做不到浏览器的排版，就直接借它** —— 面板只负责决定「交给浏览器的 HTML」，
分页、预览、打印都让浏览器做，「这样它总不会错」。

所以现在：**预览 = 浏览器排出来的那份 PDF**（见下一节），我们不再自己画纸、
也不再自己算断点。`paginate.ts` 与 `mountPrintView` 已经删掉。

## 两条出口

用的是**同一份不分页文档**（`printView.ts` 的 `mountPrintDocument`）：

| 按钮 | 走什么 | 用途 |
|---|---|---|
| **保存为 PDF** | 后端的 `print_pdf` → WebView2 的 `PrintToPdf` | 默认。**不弹任何对话框**，选个路径就出文件；产出是**真文字**，可选中、可搜索 |
| **打印…** | 后端的 `print_with_dialog` → `ICoreWebView2_16::ShowPrintUI(SYSTEM)` | **Windows 自己的打印对话框**：打印机列表、份数、纸张（在「首选项」里）都是系统那一套，接上打印机就能直接打 |

> 早先「打印…」走的是浏览器内嵌的打印预览（`window.print()`），还要用户自己去找
> 「使用系统对话框打印…」那行小字 —— 那条路已经去掉了，现在直接弹系统对话框。

### 两条路的参数分工（这里最容易写重复）

| | `print_pdf`（保存） | `ShowPrintUI`（打印） |
|---|---|---|
| 纸张 / 方向 | **后端**通过 COM `PageWidth/PageHeight/SetOrientation` | **打印机对话框 / 首选项**（我们不写 `@page size`） |
| 页边距 | **后端** `SetMargin*` | **CSS** `@page { margin }` |
| 缩放 | **后端** `SetScaleFactor` | **CSS** `zoom` |
| 页眉页脚 | **后端**（`headerFooter` 开关） | 系统那一套（面板里这两项**只对保存生效**） |

所以 `mountPrintDocument` 有两个开关：`cssPageSize` 与 `cssScale`。**保存那条两个都必须是
false** —— 后端已经设过了，CSS 再写一遍就是双重生效（纸张两处打架、缩放乘两次）。

> ⚠️ **系统对话框弹出来就返回**（`ShowPrintUI` 不等用户点确认）。真正的打印要等用户点了
> 确认之后才开始 —— 所以那份文档**不能**在命令返回时拆掉。`PdfExportPanel` 用
> `printDocRef` 把它挂到「下一次要挂新文档」或者面板关闭为止；不然印出来的是一页空白。

## 颜色两档

| 档 | 该做的 |
|---|---|
| **彩色**（默认） | **什么都不动** —— 屏幕上什么样就印什么样，包括底色（`--color-paper`）与你在样式目录里改过的配色 |
| **黑白** | **明度一个都不动，只把颜色去掉** |

### 黑白：为什么是 JS 不是 CSS

两条看着最省事的路都试过，都不行：

- ❗❗**`filter: grayscale(1)`** —— 语义最直白，但 Chromium 会把整棵子树**先栅格化成一张图**
  再印。实测：8 页纯文字的文档 **49KB → 1.07MB**（22 倍），真实长笔记那份是 31KB → 11.8MB。
  字也从「可选中」变成图片里的像素。
- ❗❗**`mix-blend-mode: color` 盖一层中性灰** —— 屏幕上是对的，但**打印路径直接忽略混合
  模式**：实测印出来整张纸就是 `#808080`。

所以现在是**渲染时把每个元素的计算颜色就地换成同明度的灰**（`printView.ts` 的
`grayOutTree`，只在黑白档跑）：读 `color` / `background-color` / 四条 `border-*-color`，
**先读完再写**（边读边写会每步触发一次样式重算）。文件大小回到 50KB 那一档，字还是字。

> ❗❗**换算交给浏览器，别自己解析颜色。** 第一版按 Rec.709 加权自己算，只认 `rgb()` ——
> 漏了一整类颜色：Tailwind 4 的 `/透明度` 编译成 `color-mix(in oklab, …)`，计算样式给出的是
> `oklab(0.628 0.225 0.126 / 0.7)`，连形状都不是 `rgb(...)`。
>
> 现在用 **CSS 相对颜色语法**：`oklch(from <原色> l 0 h)` —— 取原色的感知明度 `l`、彩度压成 0。
> 一行通吃 rgb / hsl / oklab / `color(display-p3 …)`，alpha 也自动保留。
> 兜底也安全：浏览器不认这条语法时整条声明失效，元素保持原色，不会变成黑块。

## 两条出口产出的差别（实测）

同一篇笔记分别走两条路，结果**不是同一个东西**：

| | **保存为 PDF**（`print_pdf`） | **打印到「Microsoft Print to PDF」**（系统对话框） |
|---|---|---|
| 纸张 | 面板里选的那张（实测 B4 **257.2×364.1mm**） | 打印机**首选项**里那张（Microsoft Print to PDF 默认 A4） |
| 页数 | 12 | 11 |
| 文字 | **真文字**：394 个字体对象、374 条 ToUnicode，可选中 / 可搜索 | ❗**没有文字层**：0 个字体、39 张 JPEG —— 那个驱动把整页**栅格化**了 |

所以：

- **要可复制 / 可搜索的 PDF，走「保存为 PDF」**；用系统打印机「另存为 PDF」出来的一定是图片。
- 这两条路的分页与排版是同一个引擎（都是 Chromium），**差别只在纸张和输出方式** ——
  打印时的纸张以打印对话框 / 首选项为准，面板里那个「纸张」只对保存生效。

## 零碎但要紧的

- **图片要先摘掉 `loading="lazy"`**：屏幕外的图在打印那一刻根本没开始加载，PDF 里是空白。
  这是 `waitForPrintable` 等的那一步。
- **打印时只留下那一份文档**：`body > *:not(.floral-print-root) { display: none }`。
  必须用 `display`，`visibility: hidden` 会留着布局空间，前面会多出空白页。
- **面板与文档都不许盖住标题栏**：主窗口 `decorations: false`，顶上那条 `h-11` 就是
  **拖窗口的手柄**，盖住它用户的第一反应是「窗口拖不动了」。
- **设置记在 `localStorage`**（`floral.pdfExport.settings`），逐项校验后回填 —— 某个字段
  坏了不该让整份设置回落到默认。旧版本留下的 `colorMode: "light"` 会被归一化成 `as-is`。
- **`@page` 留出来的那圈页边上不了色**：`html` / `body` 的背景压根铺不进去，Chromium 的
  `@page` margin box 不在 CSS 的绘制范围里。所以那圈一直是白的，**纸本身**的颜色才是要紧的。
- **命令必须声明 `async`**（Rust）：`with_webview` 的闭包在主线程上跑，同步命令也在主线程上等，
  那就是自己把自己锁死。另外 `windows` 这个 crate 是**必须**的直接依赖 —— `webview2-com`
  的完成回调宏展开成 `::windows::core::Result`，那个路径得在我们自己的 crate 里解析得到。

## 还没做

- **每张纸打印的页数（N-up）**：WebView2 的打印设置里没有这一项；系统对话框里由驱动决定。
- 页眉页脚的文案：`PrintToPdf` 那条只有标题与页脚文字两项，页码由 Chromium 画、格式改不了；
  `ShowPrintUI` 那条用系统/驱动的那一套，面板里的页眉页脚设置不参与。
- 目录、页码起始值、双面打印。
