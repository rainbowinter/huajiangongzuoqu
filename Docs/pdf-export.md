# 导出 PDF

「另存为 → PDF」打开的是一个**自己的导出界面**：左边设置、右边一叠分好页的 A4 纸，
底部一条状态栏写着共几页。两条出口：

| 按钮 | 走什么 | 什么时候用 |
|---|---|---|
| **保存为 PDF** | 后端的 `print_pdf` → WebView2 的 `PrintToPdf` | 默认。**不弹任何打印对话框**，选个路径就出文件 |
| **用系统打印机…** | `window.print()` | 要打真纸、要选别的打印机、要 N-up 时 |

## 为什么不用 `window.print()`

那条路必然弹系统打印对话框：用户得自己挑「Microsoft Print to PDF」、再去「更多设置」里
取消页眉页脚 —— 每一步都可能把结果弄成另一副样子，而代码里既看不到也管不了。

`ICoreWebView2_7::PrintToPdf` 直接写文件，页眉页脚 / 缩放 / 纸张 / 边距 / 方向 / 背景色
都在 `ICoreWebView2PrintSettings` 上（`src-tauri/src/pdf.rs`）。参数**逐项 clamp** 再交给
COM，等完成回调（60 秒超时）才报成功 —— 不然用户会拿到半截文件。

> ⚠️ 命令必须声明 `async`：`with_webview` 的闭包在主线程上跑，同步命令也在主线程上等，
> 那就是自己把自己锁死。另外 `windows` 这个 crate 是**必须**的直接依赖 —— `webview2-com`
> 的完成回调宏展开成 `::windows::core::Result`，那个路径得在我们自己的 crate 里解析得到。

## 分页是自己算的（`paginate.ts`）

预览里的一叠纸**不是**「一条长卷 + 几条虚线」，而是真的把内容摆进一张张固定大小的纸里。
这么做的原因：虚线是**估的** —— 真正的分页在打印那一刻才由排版引擎决定。

自己算之后：**预览就是产出**。打印时一张纸一个盒子 + `break-after: page`，PDF 的每一页
与预览的每一页逐页对应。

量法是**不看 margin 的**：把块 append 进当前页，然后看 `scrollHeight > clientHeight`。
行高、外边距折叠、图片高度全交给排版引擎，我们只读结果。切块：

- **表格按行切** —— 表头每页重画一遍，不然第二页开始的数字没有列名；
- 其它块**按行二分切**（`Range.extractContents()` 负责重建祖先链，手工搬节点最容易写出
  「标签对不上」）；
- 切不动的（一张特别高的图）**让那页长高**，绝不裁内容 —— 界面上会提示「有内容超出一页」。

### 六个踩过的坑

1. **打印时纸必须缩回「内容盒」**。第一版纸上带着页边距的内边距，一个 210×297 的盒子往
   170×261 的可打印区里塞 —— 实测 **5 张纸印成了 12 页**。
2. **量完还得再量一遍**。第一次排版时字体可能还没换好，用替身字体量的行高是错的 ——
   同一份内容字体就位前后差了**整整一页**（5 → 6）。`PrintView.settled` 就是那第二次排版，
   面板拿它刷新页数，写文件之前也必须 `await` 它。
3. **`box-sizing`**：`width: 210mm` + 左右各 20mm 内边距，在默认的 `content-box` 下就是
   250mm 宽的「纸」，比 A4 还宽。应用里 Tailwind 的 preflight 恰好兜住了，但代码里写死。
4. **表格几乎不会直接是顶层块**：预览把它包在 `my-3 relative group` > `overflow-x-auto`
   里。只认顶层 `tagName === "table"` 的话，一张大表格会被当成「切不动的 div」，按文本行
   硬切 —— **表现是表格在页底被生生截断**。所以往下找那张表（有且只有一张、且占了块高度
   一大半才算），切完把包装链照原样套回续页那一半。
5. **放不下就就地切**，别整块挪到下一页 —— 否则标题后面接一张大表格时，第一页只剩标题
   加一大片空白。
6. **`@page` 只写边距，不写 `size`**：纸张与方向已经在打印设置里给了，两处都写就是互相
   打架，而 CSS 那一条还不一定生效（Chromium 要 `preferCSSPageSize` 才认）。

## 配色三档

| 档 | 含义 |
|---|---|
| **原样**（默认） | 当前渲染成什么样就打什么样：跟着主题，表格底色、代码块、颜色一个不动 |
| 白底 | 强制浅色纸面（深色主题下想把笔记打成浅色纸时用） |
| 黑白 | 白底 + 文字全压成灰 |

「白底 / 黑白」的做法是在容器上**重新声明一套浅色 `--color-*`**，把祖先的主题挡在外面：
正文是从预览里抠出来的 HTML，那些 `text-ink-soft` 之类的类最终落到这些变量上，深色主题下
是浅灰 —— 白纸浅字，打出来几乎空白。

> ❗❗**黑白不许用 `filter: grayscale(1)`**。实测：同一份长文档，加与不加那个 filter 的页数
> 一样（10 页），但文件从 **31KB 涨到 11.8MB** —— Chromium 会把整个子树**先栅格化成一张图**
> 再印。那正是「导出来怎么变成图片了、还选不中字」的来源。所以改成**换颜色**。

## 零碎但要紧的

- **图片要先摘掉 `loading="lazy"`**：屏幕外的图在打印那一刻根本没开始加载，PDF 里是空白。
- **面板与那张纸都不许盖住标题栏**：主窗口 `decorations: false`，顶上那条 `h-11` 就是
  **拖窗口的手柄**，盖住它用户的第一反应是「窗口拖不动了」。
- **设置记在 `localStorage`**（`floral.pdfExport.settings`），逐项校验后回填 —— 某个字段
  坏了不该让整份设置回落到默认。
- **Ctrl + 滚轮**缩放预览（40%–200%）。只影响眼睛，不影响产出。
- **Ctrl+滚轮要用原生监听 + `{ passive: false }`**：React 的 `onWheel` 挂在被动监听上，
  里面 `preventDefault()` 无效 —— 结果是预览缩了、整个 WebView 的页面缩放也跟着变了。
- **不要 `window.print()`** 之外再去动 WebView2 的 ScaleFactor：缩放是用 CSS `zoom` 加在
  版心上做的，这样分页是按缩放后的版心算的，预览与产出用同一套换算。

## 还没做

- **每张纸打印的页数（N-up）**：WebView2 的打印设置里没有这一项，只有系统打印对话框有。
- 页眉页脚在**预览**里是近似画出来的：真打出来那两行由 WebView2 画在可打印区外面，
  字体与位置不完全一样（页码是它按当前页/总页数画的，文案改不了）。
- 目录、页码起始值、双面打印。
