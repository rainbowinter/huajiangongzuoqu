# 插件市场

在应用里列出可装的插件（含历史版本），点一下从网上装到本地。发布端是一个**独立仓库**，
里面只有一份清单和一堆插件包。

## 信任链

```
minisign 公钥（写在应用的 tauri.conf.json 里，可以公开）
      │ 验签
      ▼
plugin-catalog.json            ← 发布脚本用私钥签，旁边放 .sig
      │ 清单里写每个插件的 url + sha256 + apiVersion + permissions
      ▼
<名字>-<版本>.zip              ← 下载之后必须 sha256 对得上
```

**为什么必须签清单、而不是只比 sha256**：sha256 只防传输损坏，不防源头被换 —— 谁能改清单，
谁就能**同时**改 url 与 sha256，校验必然通过。签名把「装进来的东西」钉死到私钥持有者。

## 默认是关着的

```jsonc
"plugins": {
  "market": {
    "endpoints": [],          // ← 空 = 市场整体关闭
    "pubkey": ""              // ← 或者这里空着，同样等于关闭
  }
}
```

两条**缺一不可**：有清单地址没公钥的话，拿回来也验不了签，装了等于不设防，所以那种状态
也当作关闭。关闭时前端连「市场」这个页签都不显示（先问 `plugins_market_endpoint` 命令）。

字段**刻意与 `plugins.updater` 分开**：现在填的是同一把密钥，但将来想单独轮换插件市场的
密钥时只改这一处，不会牵动应用自更新。

> ⚠️ `pubkey` 要**原样**抄 `tauri signer generate` 生成的 `.pub` 文件内容 —— 那个文件本身
> 就已经是 base64 了。再编码一次是最常见的错法，而报错信息（`Invalid encoding in minisign
> data`）看不出病因，所以代码里专门把提示写长了。

## 装一个插件时到底发生了什么

```text
前置检查（地址、sha256 形状、不覆盖本地同名插件）
  → 下载（边下边算 sha256，按上限截断读）
  → 校验值对不上？停在这里 —— 一个字节都没落进插件目录
  → 解压到 plugin-install/<uuid>/（逐条路径校验，见下）
  → 复核 zip 里那份 plugin.json：apiVersion 必须是 2、入口必须真的存在
  → 写一本出身证明 .market.json
  → 换目录：旧的先 rename 进 trash/，新的再 rename 成 plugins/<名字>；失败就搬回来
  → 记状态：origin=market + grantedPermissions=Some(用户确认过的那份)
```

**写进 `plugins/` 之前做完所有校验**，所以失败不会留下半个插件。

### 解压那一步自己写，不用 `ZipArchive::extract`

它把条目名当路径直接拼上去。zip 里的名字是攻击者可控的，每一类都对应一种真实攻击：

| 攻击 | 怎么挡 |
|---|---|
| zip-slip（`../`） | 逐段校验，`.` 与 `..` 一律拒绝 |
| 绝对路径 / 盘符 | 拒绝开头的 `/`、`\`，拒绝任何 `:`（顺带干掉 NTFS 数据流） |
| 符号链接穿透 | zip 里的链接**条目**直接拒绝 |
| Windows 保留名 | `CON`/`NUL`/`COM1`… 拒绝 |
| 尾随点/空格被静默吃掉 | 拒绝 —— 否则 `a.` 与 `a` 会写成同一个文件 |
| 大小写碰撞 | 折叠后同名即拒绝（Windows/macOS 上那是同一个文件） |
| zip bomb | 单文件 4MB / 总量 48MB / 条目 512 三道上限，且**按上限截断读** |
| 头部谎报大小 | 实际写出的字节数必须与头部声明一致 |

另外约定 **zip 里恰好一层顶层目录，名字等于插件名**（`pdf-viewer/plugin.json`）。这一条
同时干掉 zip-slip 的第一层与「散文件」的歧义 —— 到底哪些文件属于这个插件。

### 只装 v2

`apiVersion` 必须 ≥ 2。v1 跑在主线程 `new Function` 里、**没有沙箱**，来自网络的代码用 v1
等于没有隔离。清单层筛一遍，**解压后再读 zip 里那份 `plugin.json` 复核一遍** —— 清单可能
过期，压缩包里的才是权威。

## 权限：确认过的那份才算数

装之前会把权限**逐条列成人话**（`PERMISSION_LABEL` 把 `workspace:read` 说成「读取工作区里的
文件」），用户点确认才发请求。用户确认的那份会被原样记进 `plugins-state.json`：

```jsonc
"grantedPermissions": ["editor:read", "ui:panel"]   // ⚠️ 一定是 Some([...])，绝不留 None
```

**为什么绝不能留 `None`**：`None` 的语义是「按清单声明全量自动授予」——插件偷偷加一个权限
就立刻生效，用户当初确认的那份清单形同虚设。写 `Some(...)` 之后，没同意过的新权限**不生效**。

连锁的两件事：

* **更新时把新增的权限重新列一遍**（`permissionsRequiringReview`），否则「装之前我确认」
  就被稀释成「第一次确认就永久放行」；
* zip 里声明的权限比清单多时，多的那几个**不授权**，但会**如实告诉用户**（「它还要 X，
  没授权，相关功能可能不可用」）—— 静默降级会让人以为插件坏了。

## 卸载

只卸**市场装的**：不看清楚就删，一条误发的命令就能端掉用户手写或随应用分发的插件。
卸载时**问清数据怎么办**（默认保留）：插件代码与数据本来就分开存（`plugins/` 与
`plugin-data/`），保留的话重装能恢复设置。

如果这个插件当初是「替换安装」装上来的，卸载会把被替换掉的那份**装回**来
（见上一节）。顺序上有一步不能反：**还原排在删数据之前** —— 备份就住在
`plugin-data/<名字>/` 下面，而「连数据一起删」会把那个目录整个删掉。

## 内置校正管不着市场插件

随应用分发的插件由 `sync.rs` 在启动时刷到最新，但它**无权过问市场插件**：内置的
`outline 2.1` 对着市场装的 `outline 3.0`，两边版本号各说各话。

判据只有一份（`market::install::is_market_origin`），两处证据看一处就够：

* `plugins-state.json` 里该插件的 `origin`（缺省 `bundled`，不写进文件）；
* 插件目录里的 `.market.json` —— 跟着目录走，状态文件被删或数据目录被搬之后仍然认得。

## 本地已有同名插件时：替换要确认，而且可逆

「本地有同名插件」有三种情形，处理方式不一样：

| 情形 | 行为 |
|---|---|
| 那个也是市场装的 | 直接更新/降级，旧的那份当垃圾清掉 |
| 随应用分发的、或用户自己写的 | 只有用户在确认框里点了「替换安装」才动，**原版备份下来** |
| 调用方没带「我同意替换」这个参数 | 后端直接拒（`marketPluginShadowsLocal`）|

**为什么留一道后端硬闸**：界面上的确认只是界面。参数传错、或者别的调用方忘了问用户，
不该能毁掉用户自己写的插件。所以 `replace_local` 缺省 `false`。

**为什么替换是可逆的**：内置插件被市场版顶掉之后，卸载就再也回不来了 —— 内置校正只更新
已装的、**从不播种**。所以：

* 被顶掉的那份**搬到** `plugin-data/<名字>/.replaced/<时间戳>/`（**不是删掉**），
  放在数据目录而不是安装工作区，因为工作区每次安装都会被清空；
* **卸载这个市场版时，原版会自动装回 `plugins/<名字>`**（`restore_replaced`），
  它随即重新归内置校正管（`origin` 回到缺省的 `bundled`）。
  备份目录名是时间戳，字典序即时间序，还原时取最新那份。

界面上的说法必须与这段代码一致，否则那个按钮与「删掉你的插件」在用户眼里没区别：
确认框会写明是**搬走**不是删掉、备份在哪儿、以及卸载会装回来（`MarketPanel.test.tsx`
里有几条专门盯这个文案的用例）。

## 清单格式

```jsonc
{
  "schema": 1,                    // 格式版本；应用不认识的会报错而不是硬解
  "catalogVersion": 7,            // 单调递增，防回滚用
  "generatedAt": "2026-10-15T12:00:00Z",
  "plugins": [
    {
      "name": "pdf-viewer",       // **目录名就是规范标识**，与本地插件同一条规矩
      "description": "…",
      "author": "…",
      "homepage": "…",
      "icon": "data:image/svg+xml;base64,…",   // 内联的图标，发布脚本从 plugin.json 的 icon 读来
      "releases": [
        {
          "version": "1.0.0",     // 必须是 1.2.3 这种数字段（可以有 -beta 后缀）
          "apiVersion": 2,
          "minAppVersion": "2.0.2",
          "url": "https://…/pdf-viewer-1.0.0.zip",
          "sha256": "…64 位十六进制…",
          "size": 1234567,
          "permissions": ["workspace:read"],
          "publishedAt": "…",
          "notes": "…"
        }
      ]
    }
  ]
}
```

两条设计取向：

* **不兼容的版本照样列出来**，只是带着原因禁用（「需要更新的插件 API」「需要花笺 9.0.0」
  「旧格式没有沙箱」）。藏起来会让用户以为市场里没这个东西，或者以为市场坏了。
* **一处写坏只影响那一条**：某个 release 少了 `sha256`，不该让整份清单解析失败 ——
  否则一个手滑的作者就能把所有人的市场打瘫。整份级别的失败只留给「不是 JSON」与
  「schema 我不认识」。

`permissions` 只用于安装前的预展示，**真值以 zip 里那份 `plugin.json` 为准**。

### 图标为什么要内联

清单里那条 `icon` 是**内联的 data URL**（不是图片地址），发布脚本从插件的 `plugin.json`
读出来做好。三个理由：

* 市场里那些插件**还没装**，本地没有它们的文件 —— 图标只能从清单来；
* 清单是签过名的静态文件，内联之后图标也跟着被签名覆盖；
* 打开市场不会为了一堆小图标额外发一串请求，离线也能看。

同样的形状本地插件那边也在用（Rust 读 `plugin.json` 的 `icon` 做一个 data URL），
所以前端只有一条渲染路径。写歪、不是图片、超过 48KB 的图标会被**丢掉**（用默认图标），
而不是把这条插件判为坏 —— 图标是装饰，不该让人装不了插件。

### 版本号必须是数字段

`1.10.0` 比 `1.9.0` 新（按数字段比，不是按字符串）。判据只有一份
（`sync::version_is_comparable`，市场与内置校正共用）：去掉 `-` / `+` 之后的部分，剩下的
按 `.` 切开，**每一段整体必须是数字**。

所以 `nightly`、`v1.0`、`1_2` 都不行 —— 拆不出数字段的版本号在应用里**没法判断新旧**。
发布脚本会直接拦下来，清单解析那边也会把它标成不可安装。

## 怎么发一个插件

```bash
# 打包 + 更新清单 + 签名（不上传）
npm run plugin -- --dir example-plugins-v2/pdf-viewer --repo <用户名>/<插件仓库>

# 顺便传上去
npm run plugin -- --dir example-plugins-v2/pdf-viewer --repo <用户名>/<插件仓库> --upload
```

脚本把清单源留在 `plugin-market/plugin-catalog.json`（**该提交**），zip 与 `.sig` 是产物
（不提交，已 gitignore）。版本号**只从插件的 `plugin.json` 读** —— 两处写版本号迟早会不一致，
而不一致的后果是「装上去的版本和清单里写的不是一个」。

约定：

* **每版一个不可变 tag**：`plugin-<名字>-v<版本>`，资产名 `<名字>-<版本>.zip`。
  同一版本**不许发第二次**（`--force` 只给「上次发布卡在半路」用）—— 允许覆盖的话，
  「已装 1.2.0」的机器永远不知道自己装的是哪一份。
* **清单放固定 tag `catalog`** 下，于是地址永久稳定：
  `https://github.com/<仓库>/releases/download/catalog/plugin-catalog.json`
  （应用会去取同名的 `.sig`）。不用 `latest` —— 那是会变的。
* **清单最后传**：先传清单的话，应用会先看到一份指向「还没传上去的 zip」的清单。
* **资产名必须纯 ASCII**：GitHub 会把以中文开头的名字吃掉，URL 静默 404（发布应用时踩过）。

## 在本地先试一遍（不用建仓库）

```bash
node scripts/market-sandbox.mjs            # 按住它，另开一个终端跑它打印的命令
```

它把 `example-plugins-v2/` 里每个插件打成 zip、造一份清单、用**测试密钥**
（`~/.tauri/market-test.key`，与生产私钥无关）签名，再在回环端口上托管，最后把配置覆盖
写进 `.devdata/market-override.json` 并打印启动命令（**要先 cd 到仓库根目录**）：

```powershell
# PowerShell：必须写 npm.cmd —— 执行策略默认拦掉 npm.ps1
cd E:\fwinter\Projects\floral-notepaper-main
npm.cmd run dev:isolated -- --config .devdata/market-override.json
```

```bash
# Git Bash / cmd
npm run dev:isolated -- --config .devdata/market-override.json
```

`--config` 是 `tauri dev` 的参数，会把那份覆盖**合并**进配置 —— 临时的，应用本身与
`tauri.conf.json` 一个字都不改。起来之后：右侧栏 → 插件 → 市场。

**托管那侧会把每个请求打出来**（`← GET /plugin-catalog.json.sig`），所以「应用真的去取签名
了」是看得见的，而不是我们假设的。逻辑层（下载、验签、解压、原子落盘、状态）有 Rust 测试
盯着；这个沙箱补的是**配置读取 → 命令 → IPC → 前端渲染**那一段，只有在真实运行时里才走得到。

⚠️ 覆盖文件里那份 `pubkey` 是**测试公钥**。别把它抄进正式配置 —— 那样应用就再也验不过
真正的清单了。

## 插件面板里的「市场有新版本」

装完之后不必自己回市场翻：**插件面板**那一行会带一个「市场有新版本 vX」的徽标和「去更新」
按钮，点了跳到市场并**高亮那一行**（列表长了以后用户根本找不到是哪一个）。

判据是 `presentation.ts` 的 `updateAvailable`：清单里那个插件的**最新可装版本**比已装的
**新**才提示。只认「更新」不认「降级」—— 用户看到「有新版本」点过去发现是降级，比不提示更糟。
两边共用 `releaseRelation`，与市场那一行按钮上的文案不会说不到一起去。

安装（含权限重新确认）仍然**只在市场那一条路上**走：插件面板那个按钮只负责带路，
不复制一套安装逻辑。

## 防回滚

签名保证清单**出自私钥持有者**，但**不保证这是最新的一份** —— 能控制端点（或能中间人）的
对手可以把昨天那份真的、签过名的清单再放回去，内容完全合法，验签也过。

所以 `catalogVersion` 必须**单调递增**，比上次见到的小就拒（记录在
`<数据目录>/plugin-market.json`）。三条细节：

* 记录里**连端点一起存**：换个市场之后，两边的版本号体系没有可比性，起点不一样就重新开始；
* **先判后写**：先写的话，一份被拒绝的旧清单已经把水位拉低了；
* **只在验签通过之后才写**：拿一份没验过签的清单去推进水位，等于把防回滚交给攻击者。

## 还没做的

* **只更新已装的**（内置插件那条规矩）—— 市场是唯一会**新增**插件的入口。
* 应用里没有「已装插件的更新提示」入口以外的批量更新：一次只装一个，装完刷新列表。
* 市场本身没有评价、下载数、搜索之外的分区 —— 清单是人写的静态文件，够用就行。
