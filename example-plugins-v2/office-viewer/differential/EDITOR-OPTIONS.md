# 开源 Word 编辑器选型调研（2026-10）

问题：花笺的 office-viewer 插件目前自己写 DOCX 解析 + 行排版 + 分页 + 编辑，
有没有"已经做好、适配了 Word 各功能按钮"的开源编辑器可以直接迁移？

**一句话结论：没有能直接替换的成品。** 只有两条路：

* **A. 整套办公套件**（ONLYOFFICE / Collabora）——功能最全、最像 Word，
  但必须跑一个常驻后端服务，桌面端离线场景代价很大；
* **B. DOCX 编辑器库**（SuperDoc / EigenPal / docen）——能嵌进现有前端、
  纯客户端，但成熟度、许可证、功能覆盖都要逐项验证，**不是"迁移"而是"换内核"**。

而且：**换引擎不等于排版自动对齐 WPS**。docen 自己的 parity 文档就写明
"pixel parity with Word/WPS" 要靠 fixture + oracle PDF 逐页比对——正是我们
`differential/` 已经在做的那套。换谁都得建这个回归网。

---

## 候选对照

| 项目 | 许可证 | 形态 | 排版保真 | 功能覆盖 | 接入花笺的代价 |
|---|---|---|---|---|---|
| **ONLYOFFICE Docs** | AGPL-3.0（社区版） | 独立文档服务器 + 前端 SDK | 高（自研排版，最接近 Word） | 最全：分节/页眉页脚/脚注/批注/修订/域/公式/图表/协同 | 很高：要打包/启动服务、做 WOPI 或回调存盘；AGPL 传染性要评估 |
| **Collabora Online** | MPL-2.0（核心 LibreOffice） | LibreOffice + WOPI 服务 | 高（LibreOffice 排版） | 很全，但 Web 端按钮/交互与 Word 有差异 | 很高：整套 LibreOffice 栈 + WOPI 服务器，体积数百 MB |
| **SuperDoc** | AGPL-3.0（可购商业授权） | 前端库（React/Vue） | 中高：DOCX-native，分页/节/页眉页脚/表格 | 编辑/批注/修订/建议 | 中：纯前端可嵌入；AGPL 对闭源分发是硬约束 |
| **EigenPal docx-editor** | Apache-2.0（`packages/pro` 等除外） | 前端库 + 无头排版 + PDF 引擎 | 中高 | 编辑/修订/协同；Office.js 子集 API | 中：React/Vue 适配器直接可用；Pro 包需商业授权 |
| **docen** | MIT | Web Components / Vue 3，canvas 排版 | 目标最高（文档网格、表格跨页、图文环绕） | 未完成：**明确标注 pre-1.0，不建议生产** | 中：零服务器、纯前端；但 API 会变，功能面要自己补 |
| **CasualOffice/docs** | Apache-2.0 | 自托管 Web 编辑器 | 未知 | 协同编辑为主 | 中高：偏"自建 Google Docs"，不是嵌入库 |
| **genoffice** | Apache-2.0 | AI Office 套件（桌面 + CLI） | 未知 | Docs/Sheets/Slides/PDF | 不适合作为嵌入式组件 |
| **TinyMCE / CKEditor 的 Word 导入导出** | 商业授权 | 富文本编辑器 + 转换服务 | 低（HTML 模型，不是 Word 排版） | 按钮多，但排版不还原 | 低技术门槛、高授权成本；**不满足"排版严格对准"** |

> 许可证提示：AGPL-3.0 的传染性覆盖"通过网络提供服务"的场景。花笺是桌面
> 应用、分发给最终用户，**闭源分发 AGPL 组件风险很高**，需要法务确认或买商业授权。
> Apache-2.0 / MIT 没有这个问题。

## 和当前自研引擎的对比

`differential/` 首轮实测（28 条排版用例）：

| 维度 | 当前 office-viewer |
|---|---|
| 文本 / 丢字 | 28/28 一致 |
| 断行 / 禁则 | 27/28 一致 |
| 分页点 | 28/28 一致 |
| 行首 x | 27/28 ≤ 0.05pt |
| 单倍行高 | **系统性 −6.8%**（已定位到 `measure.js` / `lines.js`，有校准表） |
| 功能面 | 段落/字符/列表/图片/基础编辑；缺表格、页眉页脚、脚注、分节 |

也就是说：**当前引擎的"骨架"是对的，问题集中在一个可量化的行高公式上。**
这不是"要不要换引擎"的证据，反而是"修一下就能显著收敛"的证据。

## 建议的决策顺序

1. **先修当前引擎**（1–2 天量级）
   用 `out/calibration.md` 的实测值替换 Canvas 度量；修 exact 行距的行盒定位、
   上下标基线、分页符空行。修完重跑 `differential/`，通过率应大幅上升。
   **这一步的投入产出比远高于换引擎。**

2. **如果功能面是瓶颈**（要做表格编辑、页眉页脚、脚注、修订）
   先做 2–3 天的 **spike**：拿同一个 `.docx`，分别用 SuperDoc / EigenPal / docen
   打开，跑 `differential/` 的同一批夹具，看断行/分页/行高差多少。
   这一步能直接回答"换过去到底能不能更接近 WPS"。

3. **如果选库**
   * 闭源分发 → 只能考虑 **Apache-2.0/MIT**（EigenPal 核心、docen）；
   * 能接受 AGPL 或买商业授权 → **SuperDoc** 成熟度最高；
   * 需要"Word 全部按钮" → 只有 **ONLYOFFICE**，但要接受常驻服务和体积。

4. **如果选套件**
   桌面端要塞一个本地 Document Server，启动/端口/升级/杀毒误报都要处理；
   还要解决"花笺的文件字节 → 服务端文档 → 存回磁盘"的通道。
   这是产品架构级改动，不是插件级改动。

---

## 需要你拍板的两件事

1. **分发方式**：花笺是闭源分发的商业软件吗？（决定 AGPL 能不能碰）
2. **功能边界**：表格编辑、页眉页脚、脚注、修订，哪些是"必须有"？
   如果只要"排版 + 文字输入"，修当前引擎最划算；如果要"Word 全部按钮"，
   那本质上是在重做 Office，套件是唯一现实选项。

给我这两个答案，我可以把 spike 直接跑起来：用同一批夹具对 2–3 个候选做
和 WPS 的差分，出一张"换过去能提升多少"的量化表。
